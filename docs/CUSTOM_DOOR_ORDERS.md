# سفارش ساخت درب — راهنمای پیاده‌سازی و عملیات

> Documentation review: **2026-11-07**. [Current implementation and release boundaries](CURRENT_STATE.md) is the starting point. Source, CI, published images, deployed SHA and operator/provider acceptance are separate evidence levels. Dated sections below preserve their original checkpoint and do not assert current VPS parity.

این مستند رفتار کد ماژول `custom-door-orders` را توضیح می‌دهد. هیچ مدل، رنگ،
محدودیت ساخت یا تعرفه واقعی فرملکس و دکوفیکس در migration یا seed این ماژول
منتشر نمی‌شود. مدیر باید داده‌های معتبر ایرانی یراق را وارد کند.

## بررسی مخزن و تصمیم‌های استفاده مجدد

بررسی اولیه روی شاخه `main` و درخت کاری بدون تغییر محلی انجام شد. ساختار واقعی:
NestJS / Prisma / PostgreSQL در `apps/api`، سایت Next.js با جزیره‌های React Router
در `apps/web`، پنل Next.js و MUI در `apps/admin`، قراردادهای TypeScript در
`packages/contracts`، Redis و BullMQ و ذخیره‌سازی S3-compatible. طرح احتمالی
«دو برنامه React مستقل از Next» مبنای اجرا قرار نگرفت.

| بخش موجود | استفاده در سفارش ساخت | توسعه انجام‌شده |
| --- | --- | --- |
| احراز هویت OTP و نشست مشتری | `AuthGuard` و درخواست‌های مقید به هویت جاری | مسیرهای مشتری با `CUSTOMER_OTP`؛ کنترل مالکیت در پرس‌وجوی سرور |
| پروفایل و نشانی مشتری | همان `User`، `Customer` و `CustomerAddress` | ساخت پروفایل از سرویس موجود؛ انتخاب نشانی متعلق به مشتری برای فاکتور |
| سفارش فروش | همان `Order` و شماره یکتا | `DoorOrder` با کلید یکسان، به‌عنوان افزونه تولید؛ بدون استفاده از سبد معمولی |
| پرداخت و callback | همان `Payment`، Provider، verifier و `PaymentTransition` | کل مانده از Quote جاری؛ تخصیص هر تلاش به نسخه Quote |
| پرداخت جزئی | در مسیر عادی checkout وجود نداشت | توسعه آغاز و تأیید پرداخت موجود؛ تراکنش یا درگاه موازی ایجاد نشده است |
| استرداد | همان `Refund` و مسیر ثبت مدرک پرداخت موجود | مانده از مجموع پرداخت معتبر منهای استرداد معتبر استخراج می‌شود |
| پیش‌فاکتور و فاکتور | همان `InvoiceDraft`، شماره‌گذاری، `InvoiceDocument`، انتشار و PDF | خط خدمت تولید با ارجاع به Quote؛ SKU فیزیکی جعلی ایجاد نمی‌شود |
| محصول و قیمت SKU | همان کاتالوگ و شناسه واقعی variant | تعرفه ساخت مستقل با اتصال اختیاری به SKU؛ نسخه‌های تعرفه تغییرناپذیر |
| انبار و رزرو | همان Balance، Reservation و دفتر گردش immutable | پورت تراکنشی رزرو و مصرف تولید؛ واحد پایه صحیح و برنامه مصرف واقعی |
| مدیریت و مجوز | همان layout، منو، MUI، نشست MFA و permissionها | گروه «مدیریت ساخت درب»، و کنترل ترکیبی مجوز سفارش/قیمت/انبار |
| رسانه | همان رسانه READY، اسکنر و آداپتور S3 | تصویر مدل از رسانه تأییدشده؛ فایل مرجع خصوصی با دانلود مجاز |
| اعلان | همان outbox، effect و worker پیامک | اعلان Quote، قالب اختیاری `Order`، و پیام ماندگار در پنل |
| API و خطا | همان `/api/v1`، validation، envelope و rate limiter | DTO، اعداد فارسی/عربی، OpenAPI و قرارداد مشترک جدید |
| migration و تست | همان Prisma forward migrations و Vitest/Playwright | دو migration افزایشی، تست دامنه، HTTP، DB و UI |
| استقرار VPS | همان Docker، nginx و مسیر `/admin` | بدون تغییر DNS، Cloudflare یا nginx؛ مسیرها زیر proxy موجود قرار می‌گیرند |

## معماری و داده

`DoorOrder.id` همان `Order.id` است. سفارش فروش مالک مبالغ و پرداخت‌ها باقی
می‌ماند؛ افزونه درب مالک مشخصات ساخت، Quoteها، تأیید فنی، نیازمندی و تولید است.

- `DoorModel`: نوع FORMLEX/DECOFIX، انتشار، نسخه، گزینه‌ها و قواعد فنی/محاسباتی.
- `DoorMaterial`: شیشه، پروفیل، یراق یا خدمت؛ نرخ و واحد، اعتبار، رنگ، ضخامت و SKU اختیاری.
- `DoorCatalogRevision`: Snapshot تغییرات مدل، تعرفه، نمایش دکمه و سیاست اعلان، با ثبت‌کننده.
- `DoorOrderItem`: ابعاد میلی‌متری، تعداد، انتخاب‌ها و یادداشت؛ پس از ارسال قابل بازنویسی نیست.
- `DoorQuotation`: نسخه append-only با Snapshot مدل‌ها، متریال، محاسبه و قیمت قطعی.
- `DoorPaymentAllocation`: ارتباط یکتای پرداخت موجود با Quote و هدف DEPOSIT/SETTLEMENT.
- `DoorMaterialRequirement`: Snapshot مصرف محاسباتی و ارتباط جداگانه با رزرو/مصرف واقعی.
- `DoorProductionRecord`: تاریخچه و پیام‌های append-only؛ داده‌های حساس در audit عمومی درج نمی‌شوند.
- `DoorAttachment`: فایل خصوصی اسکن‌شده، checksum و کلید quarantine؛ کلید در API مشتری منتشر نمی‌شود.
- `DoorCommand`: کلید و fingerprint دائمی برای replay دستورها.

FK، index، قیود پول و نسخه، و triggerهای PostgreSQL از تاریخچه Quote، تعرفه،
تخصیص پرداخت و مشخصات تأییدشده محافظت می‌کنند. تغییر nullable در خطوط فاکتور فقط
برای خدمت تولید مجاز است؛ trigger جداگانه، قرارداد SKU و OrderItem فروش عادی را
همچنان اجباری نگه می‌دارد. هیچ migration تاریخی بازنویسی نشده است.

## جریان مشتری

مسیر عمومی `/custom-doors` معرفی خدمت و سه مرحله انتخاب مدل، مشخصات/ابعاد و
بازبینی را نمایش می‌دهد. گزینه‌ها فقط از API دریافت می‌شوند. نبود مدل یا تصویر
واقعی به‌صورت Empty State یا جای‌نگهدار صریح نمایش داده می‌شود.

تا ۵۰ ردیف با تعداد حداکثر ۱۰۰۰ در هر ردیف قابل ثبت، ویرایش، تکثیر و حذف است؛
این اعداد حدود عملیاتی API هستند، نه محدودیت مهندسی تولید. ابعاد مثبت صحیح
میلی‌متری و اعداد فارسی، عربی و لاتین پذیرفته می‌شوند. محدوده واقعی مدل فقط از
تنظیمات مدیر می‌آید؛ نبود قواعد یا خروج از محدوده، بررسی دستی ایجاد می‌کند.
ترکیب ناسازگار در UI غیرفعال و در API نیز رد می‌شود.

فرم در جابه‌جایی مراحل حفظ می‌شود؛ ردیف‌ها در sessionStorage همان هویت نگه داشته
می‌شوند. اطلاعات ناشناس هنگام ورود در همان تب منتقل و از بخش ناشناس پاک می‌شود.
کلید و payload ثبت نامطمئن نیز برای retry پس از reload حفظ می‌شوند. فایل انتخابی
مرورگر پس از reload باید دوباره انتخاب شود. پیش‌نویس سروری نیز قابل ذخیره، ویرایش
و ارسال است؛ هنگام ارسال دوباره از تعرفه جاری محاسبه می‌شود.

فهرست و جزئیات checkout عادی مشتری، سفارش ساخت را وارد مسیر پرداخت کامل سبد
نمی‌کنند؛ پیگیری و پرداخت آن از مسیر اختصاصی انجام می‌شود.

پس از ثبت، مسیر `/account/custom-doors` و `/account/custom-doors/:id` وضعیت،
مشخصات، نسخه‌های پیش‌فاکتور، پرداخت/استرداد، مانده، رسید، پیام و فایل‌ها را نمایش
می‌دهد. مشتری باید نسخه قطعی مشخصات و مبلغ را بپذیرد؛ تا آن زمان درگاه فعال نیست.
چاپ/ذخیره پیش‌فاکتور و رسیدها در مرورگر پشتیبانی می‌شود. فاکتور رسمی منتشرشده
از بخش فاکتورهای موجود حساب کاربری قابل دریافت است.

## دکمه شناور و موبایل

`DoorOrderFloatingLink` در صفحات عمومی به صفحه پیکربندی لینک می‌دهد. نمایش از
تنظیمات مدیر کنترل می‌شود؛ در خطای دریافت سیاست، دکمه پنهان می‌ماند. تغییر سیاست
در بارگذاری جدید پوسته سایت خوانده می‌شود.

ناوبری موبایل با ResizeObserver مقدار `--mobile-nav-height` و نوار محصول مقدار
`--product-dock-height` را نگه می‌دارند. دکمه در هر دو حالت قیمت و منوی محصول،
بالاتر از ارتفاع واقعی نوار و با فاصله اضافه قرار می‌گیرد. safe-area در ارتفاع
نوار لحاظ شده است. در حساب، سبد، تکمیل سفارش، پرداخت و خود پیکربندی نمایش ندارد؛
در موبایل هنگام تمرکز روی ورودی نیز پنهان می‌شود. لینک دارای نام قابل دسترس،
آیکون تزئینی و focus است. تست مرورگر فاصله هندسی را در عرض‌های ۳۷۵، ۳۹۳ و ۱۴۴۰
پیکسل و در هر دو حالت نوار محصول بررسی می‌کند.

## قیمت‌گذاری

همه مبالغ صحیح ریالی (`IRR`) و از جنس bigint در سرور / string در قرارداد هستند.
قیمت یا وضعیت مالی ارسال‌شده مشتری قابل قبول نیست.

هر مدل چند جزء با مبنای AREA، PERIMETER، WIDTH، HEIGHT یا FIXED دارد. هر جزء
گزینه متریال مربوط، ضریب/مخرج مصرف، کسر ابعاد برش، پرت به واحد پایه و حداقل مقدار
قابل محاسبه را تعریف می‌کند. مساحت به‌صورت نسبت `mm² / 1,000,000` و طول به‌صورت
`mm / 1,000` محاسبه می‌شود؛ محاسبه پول با floating point انجام نمی‌شود. حداقل مقدار
تا شش رقم اعشار دقیق دارد. پرت پس از نسبت مصرف اعمال و نتیجه با حداقل مقایسه
می‌شود. مبلغ هر جزء به ریال رو به بالا گرد می‌شود.

قیمت هر درب شامل مجموع اجزا، هزینه پردازش، اجرت ثابت و اجرت متناسب با مساحت و
هزینه‌های ویژه است؛ مالیات مصوب مدل اضافه، تخفیف کم و حداقل قیمت مدل اعمال
می‌شود. هر مدل فرمول خود را دارد. واحد تعرفه با مبنای جزء باید سازگار باشد.

اگر قواعد، اجرت و تمام نرخ‌ها معتبر باشند و بررسی دستی لازم نباشد،
Quote خودکار قطعی ساخته می‌شود. نبود نرخ، انقضای نرخ، نبود قواعد، محدوده خاص یا
الزام مدیر، وضعیت `PENDING_QUOTE_APPROVAL` ایجاد می‌کند و پرداخت مسدود است.

مدیر قیمت نهایی **هر ردیف**، دلیل آن، هزینه‌های اضافی با عنوان/دلیل و جمع نهایی را
ثبت می‌کند. جمع ردیف‌ها و هزینه‌های اضافی باید دقیقاً برابر مبلغ قطعی باشد.
محاسبه اولیه برای بررسی باقی می‌ماند و تأیید به نسخه جدید append-only منتهی
می‌شود. نرخ جدید، سفارش و Quote قدیمی را عوض نمی‌کند.

## پرداخت کامل و اصلاح قیمت

سفارش ساخت درب پس از تأیید قیمت قطعی و پذیرش مشخصات توسط مشتری، فقط
یک پرداخت برای کل ماندهٔ قیمت نهایی دارد. سیاست بیعانهٔ مدل در محاسبه، تأیید
قیمت و آغاز پرداخت استفاده نمی‌شود و فرم آن از پنل مدیر حذف شده است.

همان `PaymentInitiationService` مبلغ قابل پرداخت را داخل تراکنش و قفل سفارش
از «مبلغ قطعی منهای پرداخت خالص تأییدشده» محاسبه می‌کند. تلاش باز یا نامطمئن
مانع آغاز درخواست مالی تازه است. هر پرداخت جدید با تخصیص `SETTLEMENT` به
Quote معین وصل می‌شود. فراخوانی Provider بیرون تراکنش DB انجام می‌شود؛ همان
verifier، callback را با درگاه بررسی می‌کند.

سوابق قدیمی، Quoteها و پرداخت‌های بیعانه حذف یا بازنویسی نمی‌شوند. callback
تلاش قدیمی همچنان پس از بررسی واقعی درگاه ثبت می‌شود، اما پرداخت جزئی
مجوز تأیید فنی یا تولید نیست؛ درخواست بعدی تمام مانده را دریافت می‌کند.
نام ستون‌های `deposit` و enumهای `AWAITING_DEPOSIT` / `DEPOSIT_PAID` برای
سازگاری داده‌های تاریخی حفظ شده‌اند؛ برچسب کاربری، پرداخت نهایی است.
Quote جدید در فیلد سازگاری `deposit` کل مبلغ نهایی را ثبت می‌کند.
ورودی قدیمی `depositPolicy` تأیید قیمت، اختیاری و منسوخ است و نادیده گرفته می‌شود.
این تغییر به مهاجرت یا بازنویسی داده‌های تاریخی نیاز ندارد.

callback تکراری اثر مالی و انباری دوباره ندارد. callback سفارش ساخت هیچ موجودی
مصرف و fulfillment فروش آماده ایجاد نمی‌کند. فقط پس از تسویه کل، وضعیت فروش
اصلی PAID می‌شود؛ وضعیت تولید مستقل می‌ماند. بازگشت مرورگر یا جواب نامطمئن
به موفقیت تبدیل نمی‌شود. callback درب به جزئیات سفارش ساخت برمی‌گردد.

اصلاح Quote سفارش قدیمی با پرداخت جزئی فقط پیش از تأیید تولید، با دلیل، بدون پرداخت باز یا رزرو
فعال و با پذیرش دوباره مشتری مجاز است. پرداخت‌های قبلی حفظ می‌شوند؛ مبلغ جدید
نمی‌تواند از پرداخت خالص کمتر باشد مگر ابتدا استرداد معتبر ثبت شود. سفارش کاملاً
تسویه‌شده یا دارای سند صادرشده بازقیمت‌گذاری نمی‌شود. پیش‌فاکتور مالی باز نیز باید
پیش از اصلاح لغو شود.

استرداد از همان مسیر موجود ثبت مدرک واقعی در پنل درگاه انجام می‌شود؛ این API پول
منتقل نمی‌کند. لغو عادی پیش از تولید، پس از رفع پرداخت باز و استرداد کامل مجاز
است. لغو پس از شروع تولید در این مسیر مسدود است و نیازمند سیاست/سند اصلاحی
عملیاتی خارج از لغو عادی است. مانده قابل مطالبه سفارش لغوشده صفر است؛ دریافت دیرهنگام
برای آن اعتبار قابل تطبیق و بررسی استرداد محسوب می‌شود. تاریخچه پرداخت حذف نمی‌شود.

## تولید و انبار

وضعیت‌های دامنه در `DOOR_STATUSES` و انتقال‌ها در `door-state.ts` تعریف شده‌اند:

`DRAFT → PENDING_QUOTE_APPROVAL / AWAITING_DEPOSIT → DEPOSIT_PAID →
AWAITING_TECHNICAL_APPROVAL → APPROVED_FOR_PRODUCTION → IN_PRODUCTION →
QUALITY_CONTROL → READY_FOR_DELIVERY → AWAITING_SETTLEMENT / COMPLETED`

انتقال برگشتی کنترل کیفیت به تولید و لغو مراحل مجاز نیز صریح است. شروع تولید به
قیمت قطعی پذیرفته‌شده، پرداخت کامل، تأیید فنی و رزرو فعال قطعات متصل نیاز دارد.
کنترل کیفیت به ثبت مصرف واقعی، و تکمیل به تسویه و اطلاعات تحویل وابسته است.

با تأیید قیمت، BOM Snapshot ساخته می‌شود. مقدار متر/مترمربع محاسباتی برای قیمت
**مقدار کسر موجودی نیست**. مدیر محل انبار، مقدار واقعی بر اساس برنامه برش، دلیل
و تاریخ انقضا را ثبت می‌کند. همان InventoryService رزرو، آزادسازی و مصرف را در
تراکنش سفارش و با دفتر گردش اصلی انجام می‌دهد. رزرو تکراری رد و retry همان
دستور replay می‌شود. گردش مصرف با reservation به BOM و سفارش قابل ردیابی است.

`ProductVariant.inventoryUnit` به‌صورت پیش‌فرض PIECE است و داده موجود را تفسیر
دوباره نمی‌کند. SKU جدید بدون موجودی، گردش، رزرو یا اتصال متریال را می‌توان با
مجوز انبار به MM یا MM2 پیکربندی کرد؛ تغییر واحد SKU دارای سابقه در API و DB رد
می‌شود. واحد متریال باید با واحد پایه SKU یکسان باشد. پروفیل شاخه‌ای/شیشه ورقی
می‌تواند همان PIECE بماند و برنامه برش تعداد واقعی شاخه/ورق را تعیین کند.
الگوریتم بهینه‌سازی خودکار چیدمان برش در این ماژول ادعا یا اجرا نمی‌شود.

## فاکتور و گزارش

مدیر یک نشانی معتبر متعلق به همان مشتری انتخاب می‌کند و نسخه قیمت/نشانی به سفارش
فروش متصل می‌شود. `InvoiceDraftService.fromOrder` خدمت تولید را با `doorQuoteId`
و یک خط خدمت با quantity=1 می‌سازد. مقدار `sku` در این خط، **شماره مرجع سفارش**
است و variantId / orderItemId فیزیکی ندارد. مشخصات چند درب در Quote immutable
متصل باقی می‌مانند.

شماره‌گذاری، سیاست فروشنده/مالیات، مهر تغییرناپذیر، انتشار برای مشتری و PDF همان
سامانه فاکتور موجود است. سیاست فاکتور باید مبلغ قطعی شامل مالیات را بدون افزایش
تعهد مشتری بازنمایی کند؛ ناسازگاری سیاست به صدور موفق تبدیل نمی‌شود. فاکتور خدمت
از ویرایشگر SKU بازنویسی نمی‌شود. گزارش ساخت، قیمت قطعی فعال، پرداخت خالص، مانده
و شمارش مراحل را نمایش می‌دهد؛ پرداخت‌ها و اسناد در گزارش‌های اصلی نیز متصل‌اند.

## مدیریت، اعلان و فایل

بخش «مدیریت ساخت درب» زیر `/admin/custom-doors/*` (یا بدون basePath در توسعه)
مدل‌ها، شیشه، پروفیل، یراق، اجرت، قواعد قیمت، سفارش، تولید و گزارش را دارد.
اجرت/قواعد جزئی از نسخه مدل هستند و جدول تکراری جدا برای هر زیرمنو ساخته
نشده است. به‌روزرسانی‌ها optimistic version و ثبت‌کننده دارند.

مجوزهای موجود استفاده می‌شوند: catalog.read/write، pricing.read/write،
orders.read/manage، inventory.adjust، settings.manage، reports.read،
customers.read و invoices.write. تأیید Quote به **هر دو** orders.manage و
pricing.write و احراز تازه STAFF_MFA، و عملیات انبار به **هر دو** orders.manage و
inventory.adjust نیاز دارد. پنهان‌سازی UI جانشین کنترل سرور نیست.

مدیر می‌تواند قالب مصوب پیامک تأیید Quote را با پارامتر `Order` تنظیم کند.
اطلاع پنل داخل تراکنش ثبت می‌شود؛ outbox/worker موجود ارسال پیامک را دنبال
می‌کند. نبود قالب یا غیرفعال بودن Provider، ارسال واقعی محسوب نمی‌شود و نتیجه
نامطمئن خودکار تکرار نمی‌شود.

فایل مرجع حداکثر ۸ MiB و فقط JPEG/PNG/WebP/PDF است. MIME واقعی و اسکن موفق
الزامی‌اند. سقف هر سفارش ۲۰ فایل است و checksum از ثبت دوباره همان محتوا جلوگیری
می‌کند. فایل زیر `quarantine/custom-doors/` در ذخیره‌سازی موجود می‌ماند؛ دانلود
فقط پس از کنترل مالکیت یا مجوز سفارش مدیر و با `no-store` انجام می‌شود. در محیط
واقعی، اسکنر تنظیم‌نشده درخواست را رد می‌کند.

## API و قرارداد

فهرست دقیق DTOها و پاسخ‌ها در `apps/api/openapi.json` و قراردادها در
`packages/contracts/src/custom-doors.ts` قرار دارد. همه مسیرها پیشوند `/api/v1` دارند.

| مسیر | کاربرد و حفاظت |
| --- | --- |
| GET custom-doors/catalog و visibility | داده منتشرشده و سیاست دکمه |
| POST custom-doors/quote-preview | محاسبه سرور با rate limit IP |
| GET/POST custom-door-orders | فهرست متعلق به مشتری / ثبت با کلید تکرار |
| POST custom-door-orders/drafts، PUT :id/draft، POST :id/submit | پیش‌نویس؛ ویرایش با expectedVersion و Idempotency-Key |
| GET custom-door-orders/:id | جزئیات فقط متعلق به مشتری |
| POST :id/accept، payment، cancel، messages | پذیرش نسخه، همان پرداخت موجود، لغو و پیام |
| POST :id/files، GET :id/files/:fileId | فایل خصوصی، محدودیت MIME/اندازه/اسکن |
| custom-doors/admin/models، materials، history/:type/:id | مدیریت کاتالوگ و نسخه‌ها |
| custom-doors/admin/visibility، notification، stock-unit | تنظیم نمایش، قالب مصوب و واحد SKU جدید |
| custom-doors/admin/orders و orders/:id | فهرست و جزئیات با مجوز سفارش |
| POST orders/:id/quote، technical، status، messages | دستورهای نسخه‌دار، مجوزهای دامنه و audit |
| POST orders/:id/materials/:requirementId/reserve / consume / release | مقدار واقعی و پورت انبار موجود |
| GET orders/:id/invoice-addresses، POST orders/:id/invoice-source | نشانی همان مشتری و پیش‌فاکتور موجود |
| GET custom-doors/admin/report | گزارش محافظت‌شده با reports.read |

Idempotency-Key در دستورهای سفارش و پرداخت اجباری است. مبلغ قابل پرداخت، نسخه
Quote و وضعیت مالی از سرور استخراج می‌شوند. خطاهای ۴xx/۵xx به موفقیت تبدیل
نمی‌شوند. کلید ثابت و payload ثابت برای نتیجه نامطمئن نگه داشته شود.

## استقرار و پذیرش واقعی

دو migration افزایشی:

1. `20261103120000_custom_door_orders`
2. `20261103140000_custom_door_invoice_identity_guard`

متغیر محیطی تازه‌ای برای فعال‌کردن فروش لازم نیست؛ همان DATABASE_URL، REDIS_URL،
تنظیمات gateway/callback، OBJECT_STORAGE_* و PRODUCT_MEDIA_SCANNER_* استفاده
می‌شوند. قالب پیامک و تنظیمات خدمت در DB مدیریت می‌شوند. Provider، فایل و SMS
باید با همان معیارهای پذیرش عملیاتی پروژه بررسی شوند.

ترتیب انتشار پیشنهادی: backup قابل بازیابی و restore تأییدشده production؛ اجرای
migration با دستور موجود `pnpm --filter @iranyaragh/api prisma:deploy`؛ به‌روزرسانی
workerهای outbox/SMS؛ API؛ سپس web/admin. پس از آن مدل و تعرفه معتبر را وارد و
سفر سفارش را در محیط پذیرش کنترل کنید. worker قدیمی موضوع جدید Quote را
نمی‌شناسد؛ آن را هم‌زمان با قابلیت به‌روز کنید و در صورت نیاز از replay موجود
outbox استفاده کنید. برای rollback، migration و تاریخچه مالی حذف نمی‌شوند.

مسیرهای عمومی، حساب و API توسط proxy موجود پوشش داده می‌شوند. سقف فایل ۸ MiB
زیر سقف ۱۲ MiB vhost موجود است. سیاست bucket و deny مسیر quarantine باید همان
حفاظت موجود را حفظ کنند. هیچ تغییر nginx، DNS یا Cloudflare برای این تحویل لازم
نشده است.

در این مأموریت migration، پرداخت واقعی یا انتشار روی VPS production اجرا نشده
است. تست Provider با Mock، اثبات پذیرش زرین‌پال واقعی نیست. restore ثبت‌شده در
گزارش تست مربوط به دیتابیس مصنوعی محلی است و جایگزین restore production نیست.

## اجرای تست

دستورات واقعی مخزن:

```sh
pnpm typecheck
pnpm lint
VITEST_MAX_WORKERS=4 pnpm test --concurrency=1
pnpm --filter @iranyaragh/api test:integration
pnpm --filter @iranyaragh/api openapi:generate
pnpm --filter @iranyaragh/e2e exec playwright test --config playwright.custom-doors.config.ts
pnpm build --concurrency=1
```

تست integration فقط با NODE_ENV=test، PostgreSQL جداگانه با نام خاتمه‌یافته به
`_test`، timezone=UTC و Redis تست اجرا شود. fixtureهای دامنه مصنوعی و با TEST ONLY
مشخص‌اند. نقش پایه از seed تست موجود تأمین می‌شود؛ seed هرگز روی فروش واقعی
اجرا نشود. تست مرورگر اختصاصی، API کاتالوگ را صریحاً intercept می‌کند؛ تست واقعی
تراکنش DB/Provider Mock در suite بک‌اند است. تصاویر Playwright در
`e2e/test-results/custom-doors` تولید می‌شوند.

نتایج واقعی و محدودیت‌های تحویل در `CUSTOM_DOOR_VALIDATION.md` ثبت می‌شوند.

## وضعیت تنظیمات ساخت و پرداخت — بازبینی ۲۰۲۶-۱۱-۰۷

- پرداخت سفارش جدید، کل ماندهٔ مبلغ نهایی پس از پذیرش قیمت است. پیشروی تولید
  به تسویهٔ کامل وابسته است؛ نام ستون‌ها/enumهای قدیمی، قرارداد جدید بیعانه ایجاد نمی‌کند.
- رنگ پروفیل: مشکی، سفید، طلایی و برنز؛ سمت دستگیره و محل لولا: راست، چپ، بالا و پایین.
- سوراخ‌کاری استاندارد الگوی شناخته‌شدهٔ کارگاه است و فاصلهٔ ساختگی ندارد. حالت
  سفارشی چهار فاصله با مرجع مستقل بالا/پایین می‌گیرد؛ UI سانتی‌متر و قرارداد
  سرور میلی‌متر صحیح است. مقدار بیش از ارتفاع واقعی و موقعیت فیزیکی تکراری رد می‌شود.
- فاصله‌های ۱۲، ۷۱، ۱۲۹ و ۱۸۸ سانتی‌متر پیش‌فرض تحمیلی نیستند؛ کاربر حالت سفارشی را وارد می‌کند.
- رنگ/متریال و تصاویر دکوفیکس از کاتالوگ قابل مدیریت می‌آیند. ضخامت ۴ میل و نرخ‌های
  تنظیم‌شده، دادهٔ فروشگاه‌اند؛ تعرفه را از seed یا عدد ثابت کد بازنویسی نکنید.
- تصاویر نمونهٔ رنگ‌ها آزمایشی/نمایشی هستند و جای فایل واقعی صاحب فروشگاه را نمی‌گیرند.
  پنل، راهنمای نسبت تصویر و ابعاد فایل اصلی/نسخهٔ نمایشی را نشان می‌دهد.
